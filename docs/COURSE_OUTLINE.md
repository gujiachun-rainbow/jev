# Jev 实战：为 LangChain Agent 构建可控的判断流程

配套阅读：[HTML 学员讲义](course.html)，可直接用浏览器打开；正文、样式与交互均支持离线使用。

面向已经使用过 LangChain Agent 的 Python 开发人员。课程从已有 Agent 的业务判断问题切入，通过项目现有案例，完成“理解 Jev → 设计问题 → 接入 Agent → 验证业务行为”的学习闭环。

建议安排为 **6 小时授课与课堂练习 + 2 小时课后综合作业**。可拆为两次各 3 小时的工作坊；休息时间另计。所有案例均以当前仓库为准，课堂实验步骤见 [COURSE_LABS.md](COURSE_LABS.md)。

## 一、学员基础与学习成果

默认学员已经理解 `create_agent`、工具调用、消息历史和基本的模型配置，不重新讲解 Agent 入门、LangChain 安装原理或 ReAct 基础。课前按 [README.md](../README.md) 配好 Python 3.10+、依赖及 API Key；无法连接 API 的学员可先做离线阈值实验。

完成课程后，学员应能：

1. 解释 TypeSafe、Jev、Python SDK 和 LangChain Agent 的关系。
2. 将业务判断拆成 Choice、Score、Noul 问题，并定义明确的评价标准。
3. 正确读取概率、分数与置信度，写出带澄清分支的业务逻辑。
4. 根据需求选择前置判断、工具内部判断或逐轮检查三种接入位置。
5. 用正例、反例和边界样本验证流程，区分模型判断质量与代码执行正确性。

结课交付：一个可运行的 Jev + Agent 业务流程、一份标注样本集，以及一页记录错误案例和阈值取舍的说明。

## 二、课程主张：哪些事情交给谁

Jev 是 TypeSafe 的模型，通过 `state + questions` 接收待判断信息和有类型的问题，返回供程序读取的结构化答案。TypeSafe 是平台与 API，`typesafe-sdk` 是本项目使用的 Python 客户端；LangChain 组织 Agent 执行流程。本项目中 DeepSeek 负责对话、工具调用和最终回复。官方将这类结构化判断模型称为 System One，课程介绍其使用方式，不将该称呼当作性能结论。[官方介绍](https://docs.typesafe.ai/introduction)

| 工作 | 本课程的责任划分 | 项目例子 |
| --- | --- | --- |
| 有明确规则的计算、过滤 | Python | 商品价格不能超过预算 |
| 从语义中分类、评估、判断条件 | Jev | 物流还是售后、用途匹配程度、是否提供了环境 |
| 对话组织、工具调用、解释结果 | DeepSeek Agent | 追问预算、查询订单、说明推荐取舍 |
| 控制分支、可用工具和执行条件 | 应用代码 | 信息不足时不给排查工具 |

普通 LLM 也能借助结构化输出完成分类。课程讨论的重点是问题接口、判断与生成的分工，以及可观察的业务行为；不预设 Jev 在所有任务上更快、更便宜或更准确。开放式写作、长期规划仍留给生成式模型；精确数值比较留给代码。

## 四、逐章教学设计

### 第 1 章：从 Agent 到结构化判断（30 分钟）

**引入问题：** 客服 Agent 同时要理解诉求、决定工具、判断是否缺信息、生成回复。哪些判断值得显式建模？

- 讲解 10 分钟：Jev 的定位；模型、API、SDK 与 Agent 框架的关系；生成回复与结构化判断的分工。
- 演示 10 分钟：运行 `main.py --json`，在一份工单上观察分类、情绪评分、紧急性判断；沿 `state → questions → result` 阅读代码。
- 讨论 10 分钟：让学员拆解自己的 Agent，标出一个语义判断点和一个确定性规则。

**验收：** 学员能说明 Jev 输出如何供程序使用，以及为何“输出结构可用”不等于“判断一定正确”。

### 第 2 章：三种原语与结果语义（45 分钟）

先用下表建立选型，再跑三个小案例。讲解 20 分钟，演示 15 分钟，练习 10 分钟。

| 类型 | 适用问题 | 关键返回值 | 必须讲清的误区 |
| --- | --- | --- | --- |
| Choice | 应该去哪个互斥类别？ | `choice`、`probabilities`、`confidence` | 置信度不能直接当作所选类别的概率或实测正确率 |
| Score | 在有序标准上处于什么程度？ | `score`、`probabilities`、`confidence` | 三档标准是 0～2；分数可为小数，不是百分制 |
| Noul | 某个条件是否成立？ | `noul`，0～1 | 表示“是”的概率，不是布尔值或程度分数；没有独立 confidence |

对应官方定义：[Choice](https://docs.typesafe.ai/primitives/choice)、[Score](https://docs.typesafe.ai/primitives/score)、[Noul](https://docs.typesafe.ai/primitives/noul)。

**案例安排：** 电商售后分类 → 软件缺陷严重程度与报告质量 → 是否要求人工、退款及重复咨询。

**课堂练习：** 将“用户是否着急”“用户有多愤怒”“该分给哪个团队”“金额是否大于 500”分别分配给 Noul、Score、Choice、Python，并解释理由。

**验收：** 能从 Score 的等级概率算出加权分数；不会用 `bool(noul)` 判断条件是否成立。

### 第 3 章：设计问题和评价标准（45 分钟）

**引入问题：** 同样叫“退款问题”，咨询规则与查询进度如何区分？

- 讲解 15 分钟：`state` 提供事实，`instructions` 定义问题，`criteria` 描述判定依据；问题 ID 用于对应结果，实际问题要写在 instructions 中。
- 演示 15 分钟：阅读 `case_advanced.py`，比较字符串标准与包含定义、排除条件、例子的结构化标准；运行 `case_mixed.py`，观察多个独立判断如何由 Python 组合。
- 练习 15 分钟：为“退货规则”和“退款进度”各写一个正例与一个易混淆反例，修改标准并复测。

多个问题可以放进一次调用，但不能假定其中一个问题能读到另一个问题的答案。存在依赖时，在代码中组合结果或分步调用。候选项来自业务数据时可动态构建问题，扩展阅读 `case_matching.py`。[结构化标准](https://docs.typesafe.ai/primitives/advanced)、[独立问题与代码组合](https://docs.typesafe.ai/introduction)

**验收：** 不把“严重程度、紧急程度、信息完整度”挤进一个含糊评分；能处理类别覆盖不足和证据缺失。

### 第 4 章：实战一——前置分流（45 分钟）

**链路：** 用户输入 → Jev Choice → Python 判断类别和置信度 → 物流 / 售后 Agent → 对应工具 → 回复；无法确定时先澄清。

- 讲解 10 分钟：适合“每条请求都必须检查”的固定前置节点；谁控制工具集合，谁生成回答。
- 演示 15 分钟：依次运行物流、售后、无法归类三类输入；查看完整类别概率、置信度、阈值和最终分支。
- 练习 15 分钟：使用 `--min-confidence` 调整阈值；给多意图输入设计澄清话术。
- 复盘 5 分钟：高置信度的 `unclear` 仍进入澄清；缺订单号与意图不明是不同问题。

**关键代码：** `select_route()`、工具列表、`create_agent()`、`agent.invoke()`。

**验收：** 对未知订单不编造状态；能解释为什么降低阈值可能减少澄清，也可能增加误分流。

### 第 5 章：实战二——工具内部判断（45 分钟）

**链路：** 用户需求 → Agent 提取工具参数 → Python 按预算筛选 → Jev 对候选商品评分 → Python 排序 → Agent 解释取舍。

- 讲解 10 分钟：适合由 Agent 根据上下文调用的能力；工具输入是生成模型提供的参数，需要应用验证。
- 演示 15 分钟：办公通勤与游戏需求分别测试；观察工具参数、候选商品和排名变化。
- 练习 15 分钟：测试缺预算、预算不足、恰好等于价格的边界；为所有商品都不匹配的情况设计拒绝推荐规则。
- 复盘 5 分钟：排序第一不等于足够适合；Jev 分数不是对生成的推荐理由逐句作证。

**关键代码：** `within_budget()`、`evaluate_products()`、动态 `questions`、排序与工具结果。

**验收：** 不推荐预算外商品；没有候选时不调用 Jev；能区分确定性价格过滤与语义匹配判断。当前示例的低匹配度说明由 Agent 提示词引导，硬性拒绝推荐作为学员扩展任务。

### 第 6 章：实战三——多轮信息检查（45 分钟）

**链路：** 累积用户事实 → 每轮 Jev Noul 检查 → 缺信息则追问 → 满足门槛才开放手册工具 → 根据手册回复。

- 讲解 10 分钟：区分对话历史与用于判断的事实；三个字段分别判断，再由代码组合。
- 演示 15 分钟：运行默认两轮流程，观察缺失项如何消失，工具集合如何变化。
- 练习 15 分钟：用 `--presence-threshold` 改门槛；给只补充浏览器、没有补充症状和步骤的输入设计第三轮。
- 复盘 5 分钟：信息“已提供”不代表事实已被外部验证，也不代表已经知道根因。

**关键代码：** `user_statements`、`messages`、`missing_information()` 和逐轮 `tools`。

**验收：** Agent 追问中的浏览器示例不能成为用户事实；信息不足时不提供排查工具；HTTP 500 不能直接推断唯一根因。

当前实现是进程内预设对话演示，未实现持久化会话、用户信息纠正合并或无限轮追问控制；这些作为工程讨论题。

### 第 7 章：验证阈值、质量与运行行为（45 分钟）

- 讲解 15 分钟：将语义判断质量、Python 分支正确性、Agent 工具与回复行为分开验证。
- 演示 10 分钟：运行 `course_threshold_lab.py`，固定回答改变阈值，观察流程变化；再运行不联网测试。
- 练习 15 分钟：按实验手册建立带期望行为的小样本集，讨论误分流和多追问的成本。
- 复盘 5 分钟：耗时必须标注测量范围；模型超时是调用失败，不能转换成“条件不成立”。

**评测设计：** 路由记录误分流率、澄清率和自动处理覆盖率；推荐记录预算违规、无候选处理与排序合理性；追问记录缺信息时错误放行及信息齐全时多余追问。先定义分母，再报告结果；调阈值的样本与最终验收样本分开。

**运行观测：** 在本地受控记录中保留输入版本、问题版本、请求/返回模型、阈值、原始判断、业务分支、调用次数、用量和耗时。推荐案例的 Agent 总耗时包含 Jev 工具耗时，不能再次相加。多次代表性请求后才讨论延迟分布，不能用一次成功调用证明性能优势。

**验收：** 能解释离线测试证明了什么、没有证明什么；不将教学阈值 0.5 / 0.8 当作通用最优值。

### 第 8 章：综合设计与迁移（60 分钟）

以“技术支持工单助手”为综合任务：识别团队、评估严重程度、检查环境/症状/步骤、决定追问或进入对应 Agent，最后引用演示工具返回的数据提出建议。

- 设计 15 分钟：画流程，决定哪些检查合并到一次 Jev 请求，哪些动作需要后续调用。
- 实现 25 分钟：复用 `case_mixed.py` 的判断方式和 `agent_case_followup.py` 的逐轮控制，完成一个最小分支。
- 演示 10 分钟：正常样本、缺信息样本、超出业务范围样本各一个。
- 评审 10 分钟：互相指出类别边界、评分标准、事实来源与兜底处理的问题。

完整实现与评测在课后 2 小时完成；本章综合项目是学员作业，不作为仓库已经实现的第四个 Agent 案例。

## 五、综合作业与评分

提交源码、运行说明、至少 12 条人工标注样本、运行记录和一页总结。12 条样本建议覆盖正常、缺失、模糊、越界四组，每组至少 3 条；另用不联网替身模拟 API 失败。样本是教学起点，不足以证明生产可靠性。

| 维度 | 分值 | 验收依据 |
| --- | --- | --- |
| 原语与标准设计 | 25 | 类型选择合理；标准可解释；单个问题目标清晰 |
| 流程与工具控制 | 30 | 缺信息先追问；不确定有兜底；业务规则由代码执行 |
| 样本与错误分析 | 25 | 记录期望和实际差异；区分模型错误与程序错误 |
| 运行与可复现性 | 20 | 配置清楚；有耗时与调用次数；失败不伪装成功 |

建议 70 分及格。编造工具结果、将 API 错误当成业务否定、把离线假想数据标成真实评测，需修正后重新验收。

## 六、授课准备与材料分工

- **主讲材料：** 本大纲用于备课；[实验手册](COURSE_LABS.md) 用于课堂操作和验收；README 用于环境与运行入口。
- **现场节奏：** 每个实战先看业务输入和流程，再看结果，最后阅读关键函数；基础脚本用于解释概念，不逐行重复讲解共同配置。
- **课前检查：** 安装锁定版本依赖、运行离线测试；讲师自行预跑需要展示的远程案例，确认 Key、模型可用性和网络。不得将 `.env` 放进投屏材料或课程分发包。
- **网络备选：** 离线阈值实验可直接使用；如使用已保存的真实响应，标注采集时间和模型。仓库已有 `timing_results.json` / `verification_results.json` 是历史记录，不当作本课程当前版本已验证的证据。
- **资料依据：** 概念按 2026-09-22 查阅的 TypeSafe 官方介绍及原语文档核对；课程编排、案例责任划分和验收任务是围绕本仓库设计的教学方案。
