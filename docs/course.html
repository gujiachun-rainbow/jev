JEV / 开发者实战课程

Jev 实战：
从语义判断到业务决策

学会用 Jev 做分类、评分与条件判断，再用代码完成分流、排序和信息检查。

课程背景

序章 为什么有 Jev

理解语义判断的常见做法、接入难点，以及 Jev 带来的变化。

假设你正在开发客服系统或商品推荐功能。用户用日常语言表达需求，程序却需要一个明确的判断结果，才能决定下一步做什么。下面用两个具体场景说明。

场景一：客服消息应该交给谁？ 一家电商平台由物流客服处理配送查询，售后客服处理退款申请。客户说“订单还没收到，帮我查查到哪了”，需要物流客服帮忙查询；如果说“订单还没收到，我不想等了，想申请退款”，则需要售后客服处理。两句话都有“订单还没收到”，但客户想办的事不同。客服系统需要理解客户是在查进度还是申请退款，才能把消息交给合适的人。

场景二：两台预算内的电脑，哪台更适合？ 用户说“预算 6000 元，经常出差，主要写文档、开视频会议，希望轻便，不玩游戏”。商店里有一台 4999 元、重 1.2 kg 的办公本，以及一台 5999 元、重 2.5 kg 的游戏本。两台都在预算内，也都能满足基本办公需求，但用户经常需要带着电脑出差，较轻的办公本更符合他的需求。推荐系统需要结合用户的用途和偏好，判断哪台更适合他。

这两个场景有一个共同点：需要理解用户话里的意思，才能做出业务判断。前者要判断客户想办理哪类业务，后者要判断商品与用户需求有多匹配。这正是 Jev 所关注的语义判断需求。

一、没有 Jev 时，这类问题怎么解决？

语义判断早已有多种实现方式。选择哪一种，取决于任务范围、数据和维护成本。

01 / 规则与关键词

把判断写成条件

例如看到“物流”就分到物流队列。规则明确、容易追踪，但“怎么还没送到”和“已经收到了，不用查物流”需要理解不同含义；只靠关键词时，往往要不断补充例外。

02 / 专用分类模型

为特定任务训练模型

用标注样本训练分类器或评分模型，可以直接输出判断。代价是准备数据、训练与维护；新增类别或改变标准时，还要评估是否需要重新训练。

03 / 通用大模型

在提示词里定义判断任务

在提示词中说明类别或评分标准，让模型理解用户需求并返回判断。接入灵活，但仍需约定输出格式、验证判断质量，并处理信息不足和误判。

展开看：通用大模型如何完成判断

怎么处理？

把用户原话和判断要求一起交给模型。例如告诉它：“查询配送进度属于物流，申请退款属于售后；请判断这条消息的类别，信息不足时返回无法确定。”对于推荐，则提供用户需求和商品资料，要求它按办公、便携等标准给每件商品打分。

怎么接入程序？

约定输出字段，例如客服返回“类别”，推荐返回“商品编号、匹配分数”。模型按要求生成文本或 JSON，程序读取结果后分流或排序。支持结构化输出的模型还可以约束字段类型和类别范围，便于程序读取。

局限在哪里？
  1. 响应耗时：简单判断也可能等待较久。 客服入口只需要一个类别，如果选用较慢的模型、启用较高的推理强度，或要求生成长篇解释，就可能增加等待时间；连续多次调用还会累积延迟。
  2. Token 成本：高频判断会放大开销。 按 Token 计费时，输入的规则、示例和商品资料，以及输出内容都会影响费用；部分推理模型的推理 Token 也计入费用。逐件评估大量商品或反复重试时，总成本会随调用量增长。
  3. 额外工作：生成了业务用不到的内容。 程序可能只读取“物流”这个类别，模型却还生成原因分析、安抚话术和处理建议；对简单分类使用过高的推理强度，也可能增加不必要的计算。这些额外工作未必提高当前判断的质量，却可能增加耗时和费用。
  4. 判断可靠性：格式正确不等于结论正确。 “查物流，也想问问退款”包含两种诉求，需要明确处理规则；商品“打 8 分”需要统一评分尺度。模型自报的“90% 把握”也不能直接当成经过校准的正确率。
  5. 维护与验证：仍需持续检验业务效果。 开发者需要用真实样本检查误判、设置追问或兜底策略，并在提示词、判断标准或模型版本变化后重新验证。

分类、评分和条件检查会在不同业务里反复出现，Jev 将这些常见需求整理成专门的判断接口。

二、有了 Jev，变化在哪里？

开发者要解决的问题Jev 提供的方式业务代码如何使用
这条消息属于哪一类？Choice：返回类别、概率分布与置信度分到对应队列；低置信度时先澄清
这个候选有多合适？Score：依据有序标准返回分数、概率分布与置信度排序、过滤，或决定是否需要复核
用户是否提供了必要信息？Noul：返回条件成立的概率按门槛判断是否继续收集信息

开发者仍然需要定义问题和标准，但返回值的类型与读取方式由接口约定。模型负责给出判断，代码显式处理阈值、兜底和后续动作；调整业务策略时，可以修改代码中的规则。

以客服分流为例 / 从输入到动作
提交消息与问题“订单还没收到”
定义物流、售后、无法确定
→
Jev 返回判断类别与概率分布
以及分类置信度
→
代码选择分支达到门槛：进入处理流程
不确定：澄清或复核

接收判断的可以是脚本、后台服务、工作流，也可以是 Agent。

三、它解决了什么，又留下哪些工作？

Jev 为常见语义判断提供了专门的接口和统一的结果形式，让开发者更容易把判断接入分流、排序和信息检查。它可以独立使用，Agent 只是可选的调用方。

通用大模型同样可以完成这类任务并返回结构化数据。Jev 是否适合你的场景，需要比较实际判断质量、延迟和成本；问题定义、样本验证、阈值选择、权限检查和失败处理仍由应用负责。

快速入门完成第一次调用

第一章 Jev 的 Hello World

准备 Python 环境，配置 API Key，写一个可以运行的 Hello World，读懂 Jev 返回的第一个判断结果。

学习一个新工具，先让它运行起来。这一章从一句 Hello, world! 你好，Jev！ 开始：把这句话交给 Jev，问它“这句话是否在打招呼？”，再用 Python 打印判断结果。你只需要会创建文件、打开终端和运行 Python 脚本。

1.1 使用 uv 准备环境

本章使用 uv 管理 Python 和虚拟环境。准备一个代码编辑器，以及可以下载依赖、访问 TypeSafe API 的网络即可。Jev 通过 API 调用，本地无需下载模型或准备显卡。

如果还没有安装 uv，请先按系统执行下面的安装命令；已安装则跳过。更多安装方式见 uv 官方安装指南。

Windows · PowerShell · 安装 uv
winget install --id=astral-sh.uv -e
macOS / Linux 安装 uv
macOS / Linux · 终端
curl -LsSf https://astral.sh/uv/install.sh | sh

安装后重新打开终端，执行 uv --version 确认安装成功。打开课程项目 jev 文件夹，在能看到 runtime.py 的项目根目录执行以下命令，创建环境并安装本章依赖：

Windows / macOS / Linux · 项目根目录
uv venv --python 3.12
uv pip install --python .venv typesafe-sdk==0.7.1 python-dotenv==1.2.3

uv venv --python 3.12 会创建 .venv 虚拟环境；如果缺少对应 Python，uv 会自动下载。本课程要求 Python 3.10 或更新版本，这里统一选用 3.12。已有符合版本要求的 .venv 时，跳过创建命令，直接安装依赖。

后续通过 uv run python 运行脚本，无需手动激活环境。本课程使用已有的 .venv 运行脚本。请在未激活其他项目环境的终端中执行。环境说明参见 uv 虚拟环境文档。

1.2 配置 API Key

登录 TypeSafe 控制台，获取自己的 API Key。在项目根目录创建名为 .env 的文件，写入下面这行，并将占位内容替换为真实 Key。已有这个文件时，补充或修改对应配置即可。

.env · 配置文件，不是终端命令
TYPESAFE_API_KEY=替换为你的真实_API_Key

项目中的 runtime.py 提供 create_client()：读取根目录的 .env，检查 Key，并创建调用 jev-latest 的客户端。系统中已设置的同名环境变量优先于文件。请将 Key 留在本地；本项目已用 .gitignore 忽略 .env。

运行前了解： 每次执行下面的程序，会把示例文本发送到 TypeSafe 并调用一次 API，可能消耗账户额度。

1.3 编写 Hello World

在项目根目录创建 hello_world.py，输入下面的代码。仓库也已提供 完整示例文件，可以直接运行。

Python · hello_world.py
"""Jev Hello World：判断一句话是否在打招呼。"""

from typesafe_sdk import Noul

from runtime import create_client


def main():
    text = "Hello, world! 你好，Jev！"
    with create_client() as client:
        result = client.system_one(
            state=text,
            questions={
                "is_greeting": Noul(instructions="这句话是否在打招呼或表达问候？"),
            },
        )

    probability = result.nouls["is_greeting"].noul
    print(f"输入：{text}")
    print(f"打招呼的概率：{probability:.2f}")


if __name__ == "__main__":
    main()

第一次阅读时，抓住下面四个部分即可：

  1. create_client()：使用刚才配置的 Key 连接 Jev。
  2. state：交给模型分析的原始文本，这里就是一句问候。
  3. questions：告诉模型要判断什么。Noul 用于询问一个条件是否成立；instructions 写具体问题。
  4. result.nouls["is_greeting"].noul：读取这个问题的结果。is_greeting 是自己起的名字，读取时要与提问时一致。

1.4 运行并查看结果

保存文件，回到项目根目录的终端执行：

Windows / macOS / Linux · 项目根目录
uv run python hello_world.py

成功后，你会看到类似下面的输出。数值仅用于说明输出格式，实际结果以你的调用为准。

输出示意 · 非实测记录
输入：Hello, world! 你好，Jev！
打招呼的概率：0.99

Noul 返回 0～1 的数值：越接近 1，越支持“这句话在打招呼”；越接近 0，越不支持。这里的结果是对文本的判断，Python 负责将它打印出来。拿到这个值，就完成了第一次 Jev 调用。

没有运行成功？按提示检查
  • 找不到 uv：安装后重新打开终端，执行 uv --version 检查；仍不可用时，按安装提示检查 PATH。
  • ModuleNotFoundError：确认在项目根目录执行了上面的 uv pip install --python .venv 安装命令，并通过 uv run python hello_world.py 运行；缺少 runtime 时，确认脚本放在课程项目根目录。
  • 提示设置 TYPESAFE_API_KEY：检查文件名是否为 .env，不是 .env.txt，并确认 Key 已填写。
  • 认证失败：检查 Key 是否有效，以及系统环境变量里是否留有旧 Key。
  • 额度不足、网络错误或超时：检查账户额度、网络连接和服务状态，然后重试。没有返回结果时，不能把它当成概率为 0。

基础概念三个基础案例

第二章 三种判断原语

类别、程度和条件对应不同的判断方式。先确定问题的含义，再选择返回值的类型。
CHOICE

是哪一类？

从固定选项中选择。
物流 / 售后 / 无法确定。

SCORE

处于什么程度？

在有序标准上评分。
无影响 / 有替代 / 完全阻塞。

NOUL

条件成立吗？

返回回答“是”的概率。
是否明确要求人工？

下面在一次请求中提出三个问题。可在项目根目录另存为脚本运行；本章后续片段均接续这里的 result，分别读取分类、评分和条件判断。

Python · 可在项目根目录另存为脚本运行；调用 Jev API
from typesafe_sdk import Choice, Noul, Score
from runtime import create_client

with create_client() as client:
    result = client.system_one(
        state="支付接口持续报错，客户都无法付款，请尽快协助。",
        questions={
            "team": Choice(
                instructions="应该由哪个团队处理根本问题？",
                criteria={"engineering": "系统或接口故障",
                          "billing": "扣款或账单争议", "other": "其他"}),
            "severity": Score(
                instructions="故障影响程度如何？",
                criteria=["不影响业务", "部分受影响但有替代方案",
                          "核心业务全部阻塞"]),
            "human": Noul(instructions="是否明确要求人工协助？"),
        },
    )
print(result.choices["team"].choice)
print(result.scores["severity"].score)
print(result.nouls["human"].noul)

questions 的键用于把请求和结果对应起来。例如 team 的答案在 result.choices["team"]。键名本身不承担问题说明；实际判定内容写在 instructions 和 criteria 中。你也可以运行 .venv/bin/python main.py --json 查看模型、答案和用量等原始返回字段。

保留确定性规则。 比如“价格不超过 6000”用 Python 比较数字；“是否适合经常出差”才需要语义判断。展示结果可以使用界面或固定模板；需要开放式解释时，可按需接入生成模型。

2.1 Choice：类别要能区分，也要能兜底

Choice 的 criteria 是选项与描述的映射。选项不具有高低顺序；你不能因为售后排在物流后面，就认为它“更严重”。对当前主诉求进行单选时，要在描述里写清如何处理重叠、未知或多意图输入。

Python · 结果读取示意，接续上面的 result
answer = result.choices["team"]
category = answer.choice             # 选中的类别
distribution = answer.probabilities   # 所有类别的概率
certainty = answer.confidence        # 分布集中程度的摘要

if category == "other" or certainty < 0.5:
    action = "先澄清"
else:
    action = "进入对应处理流程"

choice 是概率最高的选项，probabilities 给出完整分布，confidence 概括分布的集中程度。它不等于最大类别概率，也不是通过真实标签测得的正确率。即使模型十分确信选项为 other，业务仍应走范围外处理。Choice 定义 ↗

2.2 Score：先定义等级，再解释分数

给缺陷严重程度定义三个等级：0 = 不影响业务；1 = 部分功能受阻但有替代操作；2 = 核心业务阻塞。分数可以位于等级之间。假设等级概率为 {0: 0.0, 1: 0.6, 2: 0.4}，得到的是：

score = 0 × 0.0 + 1 × 0.6 + 2 × 0.4 = 1.4

这里的 1.4 是所定义尺度上的加权位置。它不是“有 70% 的概率严重”，也不是百分制成绩。不同标准下的分数不应直接比较。项目里的 case_score.py 分开评估严重程度与报告质量，因为报告写得完整并不代表问题更严重。

Python · Score 结果读取
answer = result.scores["severity"]
expected = sum(
    level * probability
    for level, probability in answer.probabilities.items()
)
print(answer.score, expected)
# SDK 的等级键为整数；原始 JSON 中的等级键是字符串。

原语定义与等级索引见 Score 文档。

2.3 Noul：概率还要经过业务策略

Noul 判断“某个条件是否成立”，返回 0～1。接近 1 表示强烈支持“是”，接近 0 表示支持“否”，接近 0.5 表示判断不确定。它没有独立的 confidence 字段。低概率表示不支持当前命题，不等于一次请求失败。

Python · 三段式策略示意；阈值需验证
p = result.nouls["human"].noul
if p >= 0.8:
    action = "登记人工诉求"
elif p <= 0.2:
    action = "未检测到明确人工诉求"
else:
    action = "进一步确认"
# 不要写 if p: —— bool(0.01) 也会得到 True。

“是否表达紧迫性”是一个条件问题；“有多愤怒”是程度问题。若你想测量程度，应该定义有序 Score 标准。概率和程度解决的是不同问题。Noul 定义 ↗

问题与标准advanced / mixed

第三章 设计判断问题

清晰的问题需要一致的输入、具体的目标和能区分类别的标准。

3.1 state 是证据，criteria 是判定依据

state 可以是文本，也可以是字典。把订单状态、用户消息、已确认的事实按结构放进去，比混在一大段提示词中更方便检查。问题应写得具体：把“看看这个客户怎么回事”改成“客户主要在咨询退货规则，还是已发起退款的进度”。

字段之间应一致。如果用户文本写“尚未申请退货”，订单对象却写“已签收”，模型面对的是矛盾证据。练习时修改文本，也要同步修改或移除过时的结构化字段。

3.2 用定义和排除条件澄清边界

Python · case_advanced.py / questions 字典节选
            "topic": Choice(
                instructions={"question": "客户主要在咨询什么？", "focus": ["message", "order"]},
                criteria={
                    "policy": {"definition": "询问退货条件或规则", "exclude": "已发起退货后的进度咨询"},
                    "status": {"definition": "查询已有退货或退款的进度", "examples": ["退款到哪里了", "退货是否签收"]},
                    "other": "不属于以上类型",
                }),

这里的 definition、exclude 和 examples 是自定义描述字段，不是特殊执行指令。它们帮助表达业务含义，不能取代后续代码校验。先用简短描述；当相邻类别频繁混淆时，再增加边界说明和代表性例子。结构化标准 ↗

输入边界解释应检查什么
“拆封后还能退吗？”退货资格与条件应倾向 policy
“退货签收四天了，退款到哪了？”已有流程的处理进度应倾向 status
“能不能退？退了多久到账？”可能同时包含两个诉求单选规则是否足够；是否需要澄清

3.3 多个问题分别判断，组合留在代码中

当工单里同时涉及团队、严重程度和人工诉求，可以在同一次请求中提出三个问题。每个问题独立看同一份 state，不能假设后一个问题已经读到前一个问题的答案。依赖答案的逻辑要在收到结果后由 Python 处理，或发起后续请求。

Python · case_mixed.py / interpret 函数体节选
    urgent = (result.choices["team"].choice == "engineering"
              and result.choices["team"].confidence >= 0.5
              and result.scores["severity"].score >= 1.5
              and result.nouls["human"].noul >= 0.8)
    return f"建议加急转技术人工：{urgent}"

这段组合逻辑表达的是“技术问题 + 达到严重程度门槛 + 明确要求人工”时建议加急。改变业务优先级时，可以直接调整代码中的条件。这个示例只是输出建议，不执行派单或退款。

把复合评分拆开。 “重要又紧急、用户又生气”的综合评分难以解释。分别评估业务影响、时间紧迫性和情绪，再写出可审查的合并规则。

实战一客服分流

第四章 客服分流

用 Choice 识别诉求，再由代码选择业务处理分支；分支可以由函数、队列或 Agent 承接。

4.1 基础路径：普通客服系统也能使用

用户消息 → Jev 分类 → 代码检查类别与置信度 → 返回物流、售后或澄清分支。普通后端可据此展示订单查询表单、返回售后规则，或把工单送入对应队列；缺订单号时用表单或固定提示补齐。这条流程不需要 Agent。

4.2 可选扩展：由专业 Agent 承接分支

下面的 agent_case_router.py 展示 Agent 接入方式。客服入口每条消息都要先确认服务范围，因此这里的 Jev 调用由 Python 固定执行。它不依赖 Agent 自己决定是否检查。确定进入物流或售后后，再创建具有对应工具的专业 Agent。

用户消息 → Jev Choice → select_route() → 专业 Agent 或澄清

4.3 从判断结果到流程分支

Python · agent_case_router.py / select_route
def select_route(answer, min_confidence=0.5):
    # 未达到阈值或类别不在允许范围时，进入澄清分支。
    if not 0 <= min_confidence <= 1:
        raise ValueError('置信度阈值必须在 0～1 之间')
    if answer.confidence < min_confidence or answer.choice not in {'logistics', 'aftersales'}:
        return 'clarify'
    return answer.choice

函数先验证阈值，再检查置信度和允许类别。它让未知类别也能进入澄清分支。边界使用 <，所以置信度恰好等于阈值时允许进入专业分支。示例默认阈值为 0.5，实际使用时应根据验证样本和误判成本调整。

LOGISTICS

物流 Agent

可用工具是 lookup_order。拿到完整订单号后查询演示物流，缺少订单号时先追问。

AFTERSALES

售后 Agent

可用工具是 lookup_return_policy。解释退货规则和所需材料，不执行退款。

类别不明与参数缺失是两类问题：“查一下物流”已经足以确定分流方向，但没有订单号；“帮我处理一下”连服务方向都不明确。前者交给专业 Agent 追问参数，后者在入口澄清。

实战二商品推荐

第五章 商品推荐

先用价格过滤满足预算的商品，再比较它们与用户用途和偏好的匹配程度。

5.1 基础路径：表单与推荐接口

表单收集用途和预算 → Python 校验并按价格过滤 → Jev 对候选评分 → 代码排序 → 页面展示结果。预算缺失时返回待补字段；没有候选时返回空列表。整个流程可以由普通接口完成，不需要 Agent 提取参数或生成回复。

5.2 可选扩展：把评估函数包装成 Agent 工具

现有 agent_case_jev_tool.py 使用这一扩展。用户说：“预算不超过 6000，经常出差，主要办公，不玩游戏。”这次由 Agent 提取用途和预算，调用 evaluate_products(requirements, max_price)。Jev 位于工具内部，只评估通过预算筛选的候选商品。

用户需求 → Agent 调用工具 → 价格过滤 → Jev 评分 → 排序与解释

5.3 硬约束先执行

def within_budget(max_price):
    # 数字大小用 Python 做确定性判断，不交给模型猜测。
    return [product for product in PRODUCTS if product['price'] <= max_price]

5.4 一个候选一个问题，一次请求完成评分

        item['id']: Score(
            instructions={'question': 'candidate 与用户用途和偏好有多匹配？', 'candidate': item},
            criteria=['与核心用途或明确偏好冲突', '满足部分需求但有明显取舍', '符合核心用途和明确偏好'],

LAB 05 / 定义最低推荐门槛

如果最好的候选也很差，怎么办？

在工具中增加最低匹配门槛：未达到时返回明确的“无推荐”结果。再单独设计低置信度的处理规则。

参考思路

低匹配表示候选与需求不合，适合建议放宽条件或补充候选；低置信度表示当前判断不确定，适合补充需求或复核。两种情况不应简单合成一个“差”。先用固定评分测试分支，再做真实语义样本验证。

实战三多轮排查

第六章 多轮信息检查

每次补充信息后重新判断，代码决定继续收集信息还是进入排查阶段。

6.1 基础路径：表单或状态机推进流程

保存用户提交的事实 → 用多个 Noul 检查环境、症状和步骤 → 代码列出缺失项 → 固定模板提示补充 → 再次提交后重检。信息齐全时，由普通函数查询手册并展示结果。多轮交互本身不要求 Agent；即使不使用聊天界面，也可以采用这套流程。

6.2 可选扩展：Agent 组织追问和工具调用

下文的 agent_case_followup.py 为现有 Agent 版本。Jev 判断和代码门槛仍然独立，Agent 负责对话及可用工具的调用。

6.3 追问是状态变化的一部分

TURN 01 / 用户报表导出有问题，帮我看一下。
Agent / 示例回复你使用什么环境或浏览器？执行了哪些操作，具体出现什么错误？
TURN 02 / 用户我用 macOS 上的 Safari 18。进入销售报表，选择九月，再点导出 PDF，就提示 HTTP 500。
下一步检查重新检查环境、症状与步骤；齐全后提供手册工具。

第一轮缺少可用于排查的细节。第二轮新增的信息可能使流程进入下一阶段。每轮都重新判断，避免把第一轮的结论永久保留下来。

6.4 对话历史不等于用户事实

案例维护两份数据。messages 存放对话，供 Agent 保持上下文；user_statements 只存用户发言，供 Jev 判断信息是否存在。如果 Agent 问“你用的是 Safari 吗？”，这句话不能被当作用户确认使用 Safari。

Python · agent_case_followup.py / 原始函数
def missing_information(result, presence_threshold=0.8):
    # Noul 是“该信息存在”的概率。低于阈值先追问，不视为已经准备好。
    if not 0 <= presence_threshold <= 1:
        raise ValueError('信息存在概率阈值必须在 0～1 之间')
    return [label for key, label in LABELS.items() if result.nouls[key].noul < presence_threshold]

三个 Noul 分别检查环境、具体症状和操作步骤。任何一项概率低于门槛，就把相应中文标签加入缺失列表。等于阈值时视为满足。这是“可否继续”的策略，不是对用户事实真实性的外部验证。

6.5 用工具可用性表达流程状态

Python · 每轮判断后的工具选择（简化片段）
if missing:
    tools = []
    instruction = "只追问缺失信息：" + "、".join(missing)

7.3 指标必须有分母

假设一批 20 条路由样本中，12 条进入业务处理分支，8 条澄清；进入业务处理分支 的 12 条里有 2 条误分流。三个指标分别为：

COVERAGE

60%

自动处理覆盖率
12 / 20

CLARIFICATION

40%

澄清率
8 / 20

MISROUTING

16.7%

自动处理误分流率
2 / 12

提高阈值可能减少误分流，也可能把更多本可处理的请求送去澄清。只看错误率容易忽略覆盖率下降。没有自动处理样本时，误分流率的分母为零，应记为“不适用”，不能写成 0%。

推荐流程重点检查预算违规、空候选处理和排序合理性；多轮流程重点检查缺信息时错误放行，以及信息齐全时多余追问。先在调参集确定规则，再用分开的验收集复核，避免只记住练习样本。

7.4 失败与耗时也属于结果

接口超时表示没有拿到有效判断，不能伪装成 Noul=0，也不能编造成功工具结果。案例脚本会报告失败并退出。业务系统可设置重试、暂存或人工接待分支，并处理重复执行的影响。

本项目的 Jev 耗时是一次 SDK 请求的端到端时间，包含网络；Agent 耗时是一次 agent.invoke()，可能含多次模型与工具调用。商品案例的 Agent 总时间已经包含工具里的 Jev 时间，两者不能相加。收集多条代表性请求后再讨论延迟分布。

用实验台比较 0.50、0.65、0.80 和 1.00，再解释：更严格的门槛会给用户带来什么额外成本？

参考思路

更严格可能增加澄清、人工复核和等待，也会降低自动处理覆盖。高置信度不保证正确，因此阈值 1 既不保证零误判，也未必符合业务目标。阈值要依据错误成本和真实样本选择。
